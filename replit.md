# Arcana Adventure - Mobile RPG Manager & Tabletop Hub

## Overview
Arcana Adventure is a full-stack web application designed to be a comprehensive hub for real-time tabletop RPG gameplay. It provides Game Masters (GMs) and players with collaborative tools for campaign management, character creation, and real-time interaction, all within a dark fantasy aesthetic. The project aims to streamline the TTRPG experience with distinct GM and player perspectives, robust role-based access control, and extensive worldbuilding capabilities. Key capabilities include interactive battle maps, dynamic character sheets, real-time chat with dice rolls, and a sophisticated world wiki system.

## User Preferences
Preferred communication style: Simple, everyday language.
Pickers: Do NOT use dropdown (`<Select>`) lists for choosing items, knowledge, or item types. Use searchable popover pickers (search box + scrollable list, like the inventory/library browser) instead.

## System Architecture

### Frontend
-   **Technology Stack**: React 18 with TypeScript, Vite, Wouter, TanStack Query.
-   **UI/UX**: Tailwind CSS v4 with a dark fantasy theme, `shadcn/ui` components (Radix UI), and Lucide React for iconography. Floating panels are used for various interactive elements, adapting to full-screen overlays on mobile.
-   **State Management**: React Context for authentication, TanStack Query for server state.
-   **Real-time Communication**: WebSockets for live updates.
-   **Key Features**:
    -   **Battle Map**: Interactive map with token management (draggable, HP/energy, initiative, GM viewport tracking), scene management, custom backgrounds, dynamic Fog of War with vision calculations (walls, doors, lighting), and GM-drawn Vision Zones.
    -   **Character Management**: Mobile-optimized character sheets with real-time updates, custom species/races, dynamic HP/energy, templates, and embedded items/spells.
    -   **Game Mechanics**: Real-time chat with dice rolls, attributes/skills, traits, rest mechanics, exhaustion, inventory with hotbars, initiative tracker, roll notifications, targeting with range/hit detection (including AOE), armor damage reduction, and combat status effects.
    -   **Progression Systems**: Interactive feat tree editor for species progression and a class-based system (AA V2) with skill trees, mana resources, and class-specific progression. Both systems support dynamic effects.
    -   **Game systems & who can pick them**: five system slugs exist — `arcana-adventure`, `aa-v2`, `aa-v3`, `ca` (C.A. / Cultivator's Adventure), and `swampy` (Swampy). The slug/label pairs live in `shared/systems.ts`; species tables key on the **display label**, everything else on the **slug**. Because the first three are incomplete, only admins may start a campaign in them — `PUBLIC_SYSTEM_SLUGS` is `['ca', 'swampy']`, enforced in the campaign-creation dropdown, the admin/My Library system picker, and `POST /api/campaigns`.
    -   **Swampy — "The Lanterns Beyond the Veil"**: built from a system brief on Daggerheart's mechanical base, with its fixed classes, Domain Cards and spellcasting removed. Rules live in `shared/swampy.ts` (independent of `shared/ca.ts` and `shared/v3.ts` both ways): six traits and freeform **Experiences** in place of any skill list; **Duality Dice** (Hope d12 + Fear d12 → five outcomes, matching dice a critical regardless of Difficulty); **HP behind Major/Severe damage thresholds** where an Armour Slot steps a hit down a tier but never below 1 HP; one **Strain** track that makes a character Vulnerable when full and spills overflow into HP damage. Magic is **Drawing** from **Warrens** (living worlds with nine conditions that shape any magic drawn from them) — there are no spells, spell slots or mana. The **Working Ledger** (`swampy_workings`) is a campaign-scoped log of precedents set in play, party-readable and GM-written; the **Deck of Houses** (`swampy_house_cards`) is drawn server-side and broadcast to the table. Warrens and cards are library content scoped `system='swampy'`, authored under Admin/My Library. Per-character state is on `swampy_*` columns; the GM's Fear pool is `campaigns.swampy_fear`. Note Swampy is **no longer a wound system** — `isWoundSystem('swampy')` is false and C.A. is the only one.
    -   **Swampy's origin as a C.A. fork (historical)**: `swampy` began as an independent copy of C.A., created so the two could diverge without either affecting the other. Its rules live in `shared/swampy.ts`, which imports nothing from `shared/ca.ts`; its per-character wound state has its own `swampy_wounds` / `swampy_body_sex` / `swampy_energy_pool` columns; and its library content is separated by the `system` slug, so Swampy's admin/My Library lanes start empty and never show C.A.'s rows. Attributes and skills still ride the shared `might`/`finesse`/… + `v3Skills` columns (a character only ever belongs to one system, so the rows can't collide — same call C.A. made against V3). The shared wound UI resolves everything through `shared/systemRules.ts`: `isWoundSystem(slug)` replaces `=== 'ca'` checks and `woundSystemRules(slug)` supplies that system's constants, helpers, and character column names. `packages/library-dialogs` is standalone and keeps its own copy of `isWoundSystem()`.
    -   **AA V3 (foundation)**: A third system value `'aa-v3'` exists alongside `'arcana-adventure'` and `'aa-v2'`. V3 admin lanes are isolated by `system` tag and start empty. V3 campaigns mirror V2 behavior for the foundation pass (mana, skill trees, item-template links, crafter recipe templates, "Effect Type" wording, mana apply-to-stat, etc. all branch on `aa-v2 || aa-v3`). External sync (CanvasRealms) currently does NOT mirror V3 rows.
    -   **AA V3 — 6-Attribute Model & Character Sheet**: V3 replaces the V2 attribute set with six attributes: Might, Finesse, Constitution, Will, Anemos, Intelligence (`characters.might/finesse/constitution/will/anemos/intelligence`, plus a `v3Skills` jsonb column). The canonical definitions live in `shared/v3.ts` (`V3_ATTRIBUTES`, `V3_ATTRIBUTE_LABELS`, `V3_SKILLS` — a fixed 19-skill list each with name/description/parentAttribute, and `attrValueToDieSides()`). Die-tier mapping by attribute value: 0→d6, 1→d8, 2→d10, 3→d12, 4+→d20. In the V3 character sheet (`V3AttrsAndSkillsTab` in `GameComponents.tsx`), the Attributes and Skills tabs are merged into one **"Attrs & Skills"** tab: an attribute grid (each attr rolls `1d{attrDie}` via `handleRoll`'s 6th `dieOverride` arg, which bypasses the V2 d20+attr-sum path) plus the canonical 19 skills shown **alphabetically** (not grouped) with descriptions; a skill roll is `1d{parentAttrDie} + skillMod`. The old V2 "Skills" tab is renamed **"Traits"** and retains custom skills + traits (the V2 standard-skills card is hidden in V3). V2 behavior is untouched (gated on `isAAV3`).
    -   **AA V3 — Species (no skill tree)**: V3 species drop the feat/skill tree and instead define `attributeBonuses` (per-attr ints), `defaultCustomSkills`, and `defaultTraits` (jsonb on both `systemSpecies` and `campaignSpecies`). On character create in a V3 campaign, `applyV3SpeciesDefaults` (server/routes.ts) adds the species' attribute bonuses onto the attr columns and inserts the default custom skills + traits tagged with `fromSpeciesId` (so they're distinguishable from player-added entries). On a species change (`PATCH /api/characters/:id` with a new `race`), `reapplyV3SpeciesOnChange` reverts the old species' attribute bonuses, deletes only the `fromSpeciesId`-tagged skills/traits (player-added ones are preserved), then applies the new species. System V3 species are resolved by the display label `'A.A. V3'` (NOT the slug `'aa-v3'`); campaign species are matched by name first. Editor UI: `V3SpeciesDefaultsEditor.tsx` (shared attribute-bonus grid + default-skills/traits lists) is rendered by the campaign species dialog (`Campaign.tsx`, feat-tree hidden for aa-v3) and by the admin `V3SystemSpeciesDialog.tsx` (replaces the package `SpeciesDialog` on the aa-v3 admin path).
    -   **AA V3 — Traits**: V3 traits have no Parent Attribute and no damage modifiers — the trait forms (`TraitForm`/`TraitEditForm` via `isAAV3` prop, and the admin `TraitFormDialog` for `systemSlug==='aa-v3'`) hide the attribute select, attr badges, damage-modifier UI, and the filter popover. V3 trait rolls add no attribute mod. **V3 trait use pool** = `usesPerLongRest + usesPerShortRest` (gated on `aa-v3` at every display/check site: `handleTraitRoll`, both hotbar tiles, token panel, character-sheet trait cards, library badge, `TraitEditForm` clamp); V2 keeps `usesPerLongRest` only.
    -   **AA V3 — Free Hotbars & Equip System**: V3 replaces the V2 battlemap/character hotbars (hidden when `aa-v3`, incl. the 'hotbars' sheet tab) with a per-user, per-campaign free hotbar (`free_hotbar_entries`: 9 loadouts × 5 slots, character OR item per slot). UI: `V3FreeHotbar.tsx` mounted in `Campaign.tsx` — loadout chevrons + H+digit shortcut, picker dialog (character search → Assign or its items; GMs also get Admin/My Library items), hold/right-click to remove. Routes at `/api/campaigns/:campaignId/free-hotbar` re-validate per-entry access on every read (revoked entries hidden; library items GM-only). Equipping: `POST /api/items/:id/equip` toggles `isEquipped`; V3 armor auto-swaps one-per-normalized-slot (`normalizeV3ArmorSlot`: chest/arm→torso, legs→leggings; equip-first ordering since Neon HTTP has no transactions). V3 armor boosts + container carry bonuses now read `isEquipped` instead of hotbar placement; inventory rows get Equip/Unequip buttons + an "Equipped" filter (V3-only). Armor-slot selects show helm/torso/leggings/boots in V3 (GameComponents ×3, AdminSettings, library-dialogs ItemDialog).
    -   **Spell Management**: System for defining spells with properties like damage, type, range, cost, and attribute.
    -   **AA V3 — Spell Crafting**: Players compose a spell from one **Core** element + 0+ **secondary** elements (each tagged with a **Role**) plus one **Intent**, **Delivery**, **Reach**, and **Duration**. Canonical enums (17 elements, 6 roles incl. Core, 15 intents, 6 deliveries, 7 reaches idx 0-6, 8 durations idx 0-7) and all math live in `shared/v3spells.ts` (`v3ManaCost`, `v3CraftDc`, `v3ElementCount`, `serializeV3Composition` for an **order-dependent** canonical hash — secondary elements hash in their listed order, so re-arranging the same parts yields a different spell, `isValidV3Composition`, `v3RoleColor`). **Mana cost** = 1/element + reachIndex + durationIndex (always consumed). **No craft roll**: crafting always succeeds — the former `1d20 + Anemos` vs Craft DC check was removed from `POST /api/v3/spells/craft` (the `v3CraftDc` helper still exists in `shared/v3spells.ts` and the DC is still stored on the spell row, but nothing rolls against it). Crafting also costs **1 Spell Creation Token** (`characters.spellCreationTokens`, max = the character's Anemos, refilled to max on long rest and seeded on V3 character create); token and mana are always consumed on craft. **NO AI** — instead, when a player crafts a brand-new composition, the server creates a `v3_spells` row with `status='awaiting_gm'` and broadcasts a `v3_spell_request` WS event; the GM authors the spell's **name, description, and profile image** (ImageBrowser) from the **Crafted Spells** manager (`V3GmSpellManager`), whose top **"Pending requests"** section lists `awaiting_gm` rows (with requester `createdByCharacterName`) and an "Author" button → POSTs `/api/v3/spells/:id/author` → `status='ready'` + `v3_spell_authored` broadcast. Authoring is non-blocking: `V3SpellAuthoringListener` (mounted in `Campaign.tsx` for `aa-v3` GMs) no longer auto-opens a dialog — it only toasts and drives a pending-count badge on the Crafted Spells button via `onPendingCountChange`. `V3SpellLiveSync` (mounted for all `aa-v3` users) invalidates `['spellbook-spells']` + `['v3-character-spells']` on `v3_spell_request`/`v3_spell_authored` so open spellbook panels/hotbar detail dialogs update in place (SpellbookPanel resolves its open detail spell from the live query by id). If a canonical (admin-approved) version already exists for that compositionHash, the row is auto-filled and created `status='ready'` with no pop-up. Admins review crafted spells in the **Crafted Spells** view on `/admin` (aa-v3 only, `V3SpellsApprovalView` in `AdminSettings.tsx`) and approve/reject; approval sets `isCanonical=true status='approved'` and demotes any prior canonical for the same hash. The author route refuses to edit canonical/approved rows (admin-only governance). Resources are deducted server-side only; on success the spell row is created **before** the deduction (the Neon HTTP driver has no interactive transactions) so a failed insert never wastes mana/tokens. Routes (`server/routes.ts` ~L6096): `POST /api/v3/spells/craft`, `POST /api/v3/spells/:id/author`, `GET /api/campaigns/:id/v3-spell-requests`, `GET /api/v3/characters/:id/spells`, `GET /api/v3/spells/canonical/:hash`, `GET /api/admin/v3-spells`, `POST /api/admin/v3-spells/:id/approve|reject`. The crafter (`V3SpellCrafter` in `client/src/components/game/V3SpellCrafter.tsx`) is a **reusable exported component** with a live color-coded formula display. **Spell levels & rolling**: a crafted spell is cast at a chosen level via the level stepper (default/min 1, no max) in `V3SpellDetailDialog`; `shared/v3spells.ts` holds the level math — `v3LevelDice(level)` (count=1+floor((lv-1)/4), die sides cycle d6/d8/d10/d12 by (lv-1)%4, no cap), `v3LevelDiceNotation`, and `v3LevelExtraMana(level)=level-1` (added to base mana). The cast (`client/src/lib/v3cast.ts` `castV3Spell`) rolls the multi-die total **client-side** (the server dice endpoint is single-die only), dispatches a roll notification, guards "Not Enough Mana", and deducts via `gameWs.sendCombatMana`. Long-press is disabled on V3 spell hotbar slots (tap still opens the detail dialog). V2 spell flow is untouched (all logic gated on `aa-v3`).
    -   **Roll Templates (AA V2 only)**: Admins create lightweight roll templates (name + roll settings only) in the unified Roll Templates view (stored as items where `isLiveTemplate=true`). Both the AAv2 admin Item AND Spell create/edit dialogs render the same `ItemTemplateLinksPanel` checkbox list, so a single template can be linked to many items AND many spells. Linking copies the template's rolls onto the owner with `fromTemplateRollId` pointers, recorded in `item_template_links` (item↔template) or `spell_template_links` (spell↔template, FK to `items.id`). Subsequent edits/additions/deletions to a template's rolls fan out automatically to every linked item AND spell, including character-owned copies, via provenance-aware propagation. Per-instance overrides: editing an inherited roll on a specific item/spell auto-flips `roll_entries.isOverridden=true`; subsequent template-roll edits skip overridden copies (untouched copies still update), template-roll deletes detach overridden copies (preserved as standalone) but delete non-overridden ones, and template unlinks behave the same way. A `RotateCcw` "Reset to template" button (`POST /api/roll-entries/:id/reset-template`) restores an overridden roll to the template's current values and clears the flag. The badge on inherited rolls shows "(modified)" in violet when overridden. Deleting a template entirely scrubs all inherited rolls across both ownerType='item' and ownerType='spell' and drops both link tables; overridden copies are preserved by detaching their provenance pointer. Owner-template detection uses `isLiveTemplate`, not `isTemplate` (the latter is also set on plain admin system-items).
    -   **Roll Item Cost**: Each roll entry can require the player to have specific admin items in their inventory before it executes (`hasItemCost` bool default false; `itemCosts` jsonb array of `{itemId, name, consumed}`). Configured in `RollEntriesEditor.tsx` via the new `ItemCostSection` collapsible (admin-item picker fed by `GET /api/admin/system-items`, which was opened from `requireAdmin` to `requireAuth` so GMs can read the picker — mutations remain admin-only). Inventory match prefers `templateItemId` then falls back to `name` so direct copies satisfy a requirement. Pre-flight check fires a system notification listing missing/available items and aborts the roll. Items flagged `consumed:true` are decremented (or deleted at qty 1) via `api.updateItem`/`api.deleteItem` AFTER all sufficiency checks (energy, mana, item cost) pass — so an aborted "Not Enough Mana" roll never wastes a consumable. Wired into all three execution paths: `handleRollEntryExecution` (BattleMapHotbarSlot, uses `allItems`), `executeSpellRoll` (CharacterSheet, uses `items` query), `executeRoll` (ItemDetailDialog, uses `items` prop). Module-level helpers `findOwnedForCost`, `checkRollItemCosts`, `consumeRollItemCosts` live near the top of `GameComponents.tsx`.
    -   **Roll Apply-to-Stat — Mana (AA V2)**: The roll-settings "Apply to Stat" dropdown now exposes a `mana` option in AA V2 campaigns only, gated by `getApplyToStatOptions(campaignSystem)` in `RollEntriesEditor.tsx`. Mirrors the existing energy branch via `gameWs.sendCombatMana` at all six apply sites: save-roll loop, AOE loop, single-target, `executeSpellRoll`, `executeRoll` no-roll branch, and `executeRoll` dice branch. Each site is gated `applyToStat === 'mana' && campaignSystem === 'aa-v2'` so non-AA-v2 campaigns silently fall through.
    -   **Skill Total Display**: Each skill row in the Skills hotbar picker (both standard and custom) now shows the skill modifier and the combined total (skill mod + linked attribute mod) in amber, e.g. `+2 = +5`. Standard skills map their 3-letter attr abbreviation (FIN/MIG/WIT/WIL/CRA/PRE) to the lowercase character column name; custom skills lowercase their `parentAttribute`. Helps players see the actual d20 modifier without doing the math.
    -   **Roll DC Check**: Each roll entry can require a DC to succeed (`hasDcCheck`). The check value is resolved by `dcCheckRollMode`: `'main'` (default) compares the main roll's total against the DC; `'separate'` rolls a fresh `1d20 + dcToSucceedAttribute` mod (with attribute "None" supported) and compares that, leaving the main roll's value untouched. The DC value is resolved by `dcToSucceedType`: `'value'` uses the static `dcToSucceed` integer; `'caster'` uses `8 + casterMod[dcToSucceedDcAttribute]`; `'target'` uses the targeted character's `naturalArmor` (their DC value) directly — the previous "8 + target attribute mod" behavior was removed because that's what Save DC does. The shared helper `resolveDcCheck(rollEntry, mainRollTotal, caster, targetChar?)` (`client/src/components/game/GameComponents.tsx`) handles both axes; the two execute paths (`executeSpellRoll` in CharacterSheet, `executeRoll` in ItemDetailDialog) call it without `targetChar`, so type='target' falls back to the static `dcToSucceed` value (or 10) in those flows. UI lives in `RollEntriesEditor.tsx` "DC to Succeed" section: Roll Mode select first, then DC Type, with `dcToSucceedAttribute` only shown in separate mode and `dcToSucceedDcAttribute` only shown in caster mode.
    -   **Roll Folder + Priority Sorting**: Each `roll_entries` row carries an optional `folder` (text) and a `priority` (int, default 1, lower sorts higher). Rolls with a folder render under a collapsible folder header that anchors at the min priority of its contents. Roll Templates (`items` where `isLiveTemplate=true`) additionally carry `templatePriority` (int, default 1) and `templateUseOwnOrder` (bool, default false). When `templateUseOwnOrder=false` (default), the template's inherited rolls interleave with the owner's other rolls by their per-roll priority. When `true`, those inherited rolls render as one contiguous template-group block anchored at `templatePriority`, ordered internally by their own priorities (folder structure inside the group is preserved). All template→owner copy paths (link toggle, item/spell create with templateLinks, item-template-links PUT, spell-template-links PUT, template-roll fanout) propagate `folder` and `priority` automatically via spread; PATCH on a template roll re-syncs both fields to non-overridden inherited copies. Server `enrichWithTemplateNames` (`server/routes.ts`) decorates each inherited roll in `GET /api/roll-entries` responses with `templateName`, `templatePriority`, `templateUseOwnOrder`, and `templateOwnerKey` so the client sort util `client/src/lib/rollSort.ts` (`sortRollsForDisplay`, `collectFolderNames`) can build the unified `roll | folder | template-group` display tree.
    -   **Notes System**: Obsidian-like note-taking with nested folders, markdown, rich text, entity references, collaborative editing, Canvas editor, and Graph View, integrated with the Worldbuilding system. The `CanvasEditor` component is reusable and supports optional providers (`noteSearchProvider`, `entitySearchProvider`, `hideNoteNodes`) for use in both Notes and World Builder contexts.
    -   **World Builder Tabs**: True browser-style tab system across the entire World Builder, in both the standalone `/worldbuilder` page (`WorldBuilder.tsx`) and the campaign-embedded panel (`WorldBuilderContent` in `Campaign.tsx`). Any section (Home, Encyclopedia, Maps, Timeline, Calendar, Graph), individual article, or map editor can be opened as its own tab. Tab types: `home | encyclopedia | article | maps | map-edit | timeline | calendar | graph`. State: `wbTabs: WbTab[]` and `activeWbTabId`. Section nav buttons create/switch tabs. Article tabs open per entity. Map editing opens a dedicated `map-edit` tab (per map, with `mapId`). Per-tab state for timeline (`selectedTimelineId`). Default click navigates in current tab; Ctrl/Cmd+click opens new tab. Home tab auto-creates on world load.
    -   **Worldbuilding Wiki System**: Unified platform for creating independent "Worlds" with articles, maps, timelines, calendars, and relationship graphs. Features include wiki-link autocomplete, public share links, visibility controls, and WebSocket live sync. Worlds can be linked to campaigns.
    -   **Battlemap Ruler / AOE Measurement Tool**: A pure measurement layer (no damage) on the battlemap, available in both AA V2 and V3. A "Ruler" button sits under the Target button in `SelectionModeButtons`; activating it reveals four shape sub-buttons (Cone, Line, Square, Circle) plus a compact value-input dialog (`ruler-control-panel`, positioned `top-14`) scoped to the selected shape (cone: length+arc; line: length+width; square: side; circle: radius — all in feet). Cone & Line originate from the active character's token projecting toward the cursor; Square & Circle snap to the clicked cell center with a thin distance-line back to the caster labeled in feet (5 ft/cell), each shape labeled with its size. Markers broadcast in real time via the battlemap WebSocket (`{type:'ruler', action:'place'|'clear'|'clearAll', marker?}` handled in `server/routes.ts`, sent via `gameWs.sendRuler` in `api.ts`) and persist until Clear (this user's markers) or GM "Clear All" (everyone's), or until the user deselects Ruler mode (which removes that user's markers and hides the sub-buttons/dialog). Types `RulerShape`/`RulerMarker` and the SVG renderer `RulerShapeSvg` live in `GameComponents.tsx`; Campaign state/handlers live in `Campaign.tsx` (`buildRulerMarker`, `handleRulerPreview/Commit`, `clearMyRulerMarkers`, `clearAllRulerMarkers`). Markers are committed on a click (no drag) at the cursor — there is no live drag-out, the size comes from the dialog inputs.
    -   **Campaign Map Pins**: Interactive pins on the battlemap with percentage-based coordinates, supporting text reveals and scene links. Pins can be marked as shops.
    -   **Shop System**: GMs manage shop inventories (items, prices, stock, currency) linked to map pins. Players can buy/sell items with automatic currency conversion and a charisma-based haggling d20 roll. Shops can be linked to shopkeeper characters for automated currency tracking.
    -   **World Collaboration**: World owners can add friends as collaborators (editors) via World Settings. Collaborators get full read/write access to all world content. Campaign wiki linking lets GMs assign a world wiki to a campaign. Per-article player access control lets GMs grant view/edit access to specific players for `player_visible` articles.
    -   **Campaign Wiki Unification (AA V2)**: In AA V2 campaigns, the World Builder replaces the Notes panel as the unified wiki for all players and GMs. The Notes button is hidden, the World Builder is always visible, and articles default to read-only view with an Edit button for authorized users. Non-GM editors can only modify content fields (articleContent, description, displayName, image, tags) -- visibility and entity type changes are GM-only. A `WikiArticleWithAccess` wrapper component fetches per-user access via `/api/worlds/:worldId/entities/:entityId/my-access` to determine edit permissions.
    -   **Preview-First Article Layout**: Both the standalone WorldBuilder and campaign-embedded wiki display articles in a "google doc" preview layout by default, matching the public SharedWorldView style. Features: hero image with gradient overlay, entity type badge, amber-bordered description, prose-invert content with interactive wiki links, and read-only tag badges. An Edit button appears at the top for users with edit access. The EntitySidePanel (Overview/Links/Refs tabs) has been removed from article views.

    -   **App Themes**: Three global themes (Cartographer's Study default, Arcane Library, Sagebound Workshop) selected in Profile dropdown → Settings → Appearance. `<html data-theme>` + `users.theme` (PUT /api/profile/theme) + localStorage `aa-theme` with a pre-render inline script for no-flash. Implementation: Tailwind stone/amber utilities are remapped to CSS vars in BOTH `index.css` and `canvasrealms/index.css` `@theme` blocks; per-theme overrides under `:root[data-theme=...]`. Section accent vars via `data-section` attrs on Campaign/Notes/CR MainLayout/AdminSettings roots.

### Backend
-   **Technology Stack**: Express.js with TypeScript, `express-session`.
-   **API Design**: RESTful endpoints, WebSocket server, session-based authentication, and role-based access control.
-   **API Scoping**: Worldbuilding data is accessible via both world-scoped and campaign-scoped routes.

### Data Storage
-   **Database**: PostgreSQL via Neon serverless, managed with Drizzle ORM.
-   **Schema**: Comprehensive schema covering all application entities, including `worlds`, `entities`, `campaign_map_pins`, `shop_items`, and `shop_haggle_rolls`. Worldbuilding tables feature `worldId` and `campaignId` (nullable) for flexible scoping.
-   **Validation**: Zod schemas for input validation.

### Authentication & Authorization
-   **Authentication**: `bcryptjs` for password hashing, session-based authentication with "Remember Me" support.
-   **Authorization**: Three-tier role system (Owner, Assistant GM, Player) and a four-tier character access permission system.
-   **Security**: Hashed passwords, session cookies, CSRF protection, and PII sanitization.
